# Module 02: SOC Team Internals

> **Overview:** This module dives into the internal operational workflows of a SOC: how L1 analysts triage alerts, write escalation reports, follow playbooks/workbooks, track performance metrics (`MTTD`/`MTTR`), and handle phishing incidents.

---

## Chapter 1: SOC L1 Alert Triage

### Event vs. Log vs. Alert
- **Event:** Any discrete action occurring on a system or network (e.g., a file is opened, a user logs in).
- **Log:** The recorded timestamped entry of an event stored on disk or sent to a SIEM.
- **Alert:** A notification generated by a SIEM, EDR, or IDS when a log (or sequence of logs) matches a specific **Detection Rule** indicating potentially malicious behavior.

### The Alert Triage Workflow
1. **Assign Ownership:** Claim the alert from the `New / Unassigned` queue and move its status to `In Progress` so other analysts don't duplicate work.
2. **Inspect Alert Metadata:**
   - Check **Alert Name**, **Severity** (`Low`, `Medium`, `High`, `Critical`), **Timestamp (UTC)**, **Rule Logic**, and **Indicators** (Hostname, User, Source/Dest IP, Process Hash).
3. **Contextual Investigation (Pivoting in the SIEM):**
   - Look at surrounding logs ($\pm 15$ minutes around the alert timestamp) on the affected host/user.
   - Query Threat Intelligence (VirusTotal, AbuseIPDB) for external IPs, domains, or SHA256 hashes.
4. **Verdict Classification:**
   - **True Positive (TP):** Confirmed malicious or unauthorized activity $\rightarrow$ **Escalate to L2** (or initiate containment per workbook).
   - **Benign True Positive (BTP):** The detection rule triggered accurately on the behavior, *but* the behavior was an authorized administrative action or scheduled penetration test.
   - **False Positive (FP):** The alert fired erroneously on normal user/system traffic $\rightarrow$ Close alert and recommend rule tuning.

## Chapter 2: SOC L1 Alert Reporting

### Writing an Effective Escalation Report
When escalating a True Positive alert to a **Tier 2 Incident Responder**, your report must be concise, factual, and immediately actionable so Tier 2 doesn't have to restart the investigation from scratch.

### The "5 Ws" of SOC Reporting
| Component | Questions to Answer | Example |
| :--- | :--- | :--- |
| **When** | Exact timestamp (always specify timezone, ideally **UTC**) of the alert and initial activity | `2026-11-16 09:14:22 UTC` |
| **Where** | Affected hostname, internal IP, OS, and business unit | `WKSTN-FIN-04 (10.10.25.14) - Windows 11` |
| **Who** | Compromised user account / privilege level and external Threat Actor IP | User `j.doe` (Standard User); Attacker IP `185.220.101.4` |
| **What** | Summary of malicious activity, executed command lines, file paths, and SHA256 hashes | Executed `powershell.exe -enc ...` spawned by `OUTLOOK.EXE`, dropping `C:\Temp\update.exe` |
| **Why / How** | Root cause / initial access vector and rule that triggered | User clicked a phishing link in email subject `"Urgent Invoice"`; triggered EDR rule `Suspicious Office Child Process` |

> **Best Practice:** Always **defang** malicious URLs and IP addresses in written reports and tickets (e.g., `185.220.101[.]4`, `hxxps://evil-domain[.]com/payload.exe`) so nobody accidentally clicks them!

## Chapter 3: SOC Workbooks and Lookups

### Playbooks, Runbooks, and Workbooks
- **Playbook / Workbook:** A standardized workflow document or interactive checklist guiding an analyst through the exact questions to ask, logs to check, and enrichment steps to perform for a specific alert category (e.g., *Impossible Travel Login*, *Malware Execution*, *SSH Brute Force*).
- **Runbook:** Tactical, step-by-step technical procedures (often automated via SOAR) for executing a specific response action (e.g., *How to isolate a host in CrowdStrike* or *How to block a domain on the Palo Alto firewall*).

### Using SIEM Lookups & Asset Inventories
To distinguish malicious activity from normal operations, analysts cross-reference raw telemetry against **Lookup Tables / Context Lists**:
- **Asset Inventory Lookup:** Maps an internal IP (`10.10.1.5`) to its hostname, owner, OS, and criticality (`Domain Controller` vs. `Guest Wi-Fi Laptop`).
- **Identity / HR Lookup:** Maps a `username` to full name, department, manager, geographic location, and employment status (e.g., is the user on vacation or recently terminated?).
- **Known Scanner / Admin IP Whitelist:** Lists authorized internal vulnerability scanners (`Nessus` IP) or IT jump boxes so analysts don't mistake routine scans for an attack.

## Chapter 4: SOC Metrics and Objectives

### Key Performance Indicators (KPIs) in a SOC
SOC Managers measure the efficiency and effectiveness of detection and response using time-based and quality-based metrics:

```text
[Compromise Begins] ----(MTTD)----> [Alert Detected] ----(MTTA)----> [Triage Starts] ----(MTTR)----> [Contained & Remediated]
```

| Metric | Full Name | Definition & Goal |
| :--- | :--- | :--- |
| **MTTD** | **Mean Time to Detect** | Average time between when an attack starts and when the SOC first detects it (Lower is better) |
| **MTTA** | **Mean Time to Acknowledge** | Average time an alert sits in the queue before an L1 analyst picks it up |
| **MTTR** | **Mean Time to Respond / Remediate** | Average time taken to contain and neutralize a confirmed incident after detection |
| **Dwell Time** | **Attacker Dwell Time** | Total duration an attacker operates undetected inside a target environment |
| **FP Rate** | **False Positive Rate** | Percentage of alerts that turn out to be benign noise (high FP rate causes **Alert Fatigue**!) |

### Agreements Governing SOC Operations
- **SLA (Service Level Agreement):** Legally binding contract (especially for **MSSPs** — Managed Security Service Providers) defining required response times (e.g., *Critical alerts must be triaged within 15 minutes*).
- **SLO (Service Level Objective):** Specific internal measurable targets (`MTTA < 10 minutes`) used to meet the overarching SLA.
- **SLI (Service Level Indicator):** The actual real-time metric observed over a period (e.g., *This week's MTTA was 7.4 minutes*).

## Chapter 5: Introduction to Phishing

### Anatomy of an Email & Delivery Flow
```text
[Sender MUA] ---> [Sender MSA/MTA (SMTP)] ---> [Internet / MX DNS Lookup] ---> [Recipient MTA] ---> [MDA (IMAP/POP3)] ---> [Recipient Inbox]
```
- **MUA (Mail User Agent):** Email client (`Outlook`, `Thunderbird`, `Gmail Web`).
- **MTA (Mail Transfer Agent):** Mail servers (`Exchange`, `Postfix`) transferring email via **SMTP**.
- **Email Components:**
  1. **SMTP Envelope (`Return-Path` / `MAIL FROM`):** Used by mail servers for routing bounces; hidden from the default inbox view.
  2. **Email Headers:** Metadata showing the exact server hops (`Received:` headers read **bottom-to-top**), authentication results (`Authentication-Results`), `From`, `To`, `Subject`, `Date`, `Message-ID`, and `X-Mailer`.
  3. **Email Body & Attachments:** Plaintext (`text/plain`), HTML (`text/html`), and Base64-encoded MIME attachments.

### Indicators of a Phishing Email
- **Sender Discrepancy:** The display name says `"Microsoft Support <support@microsoft.com>"`, but the actual `From:` address or `Reply-To:` / `Return-Path:` points to an external domain (`@mail-security-update.ru`).
- **Failed Email Authentication:** `SPF: fail/softfail`, `DKIM: fail`, or `DMARC: fail` inside the `Authentication-Results` header.
- **Psychological Triggers:** Artificial urgency (*"Your account will be suspended in 2 hours"*), authority impersonation (CEO/IT Helpdesk), or unexpected invoices/shipping notices.
- **Deceptive Hyperlinks:** Anchor text shows `https://paypal.com/login`, but the underlying HTML `href` attribute points to an attacker server or URL shortener.
